A1  [BLOCKING]  Tier 1 vision contradicts its own resolution
--------------------------------------------------------------------------------

CONFLICT
  PLAN.MD:61 promises the user installs and "does nothing... no API key
  hunting, no configuration". PLAN.MD:150 (C5) resolves to BYOK, which
  REQUIRES the user to obtain and paste a key. PLAN.MD:567 lists the gap
  as MEDIUM and "accept" - but the Part 1 text was never corrected.

EVIDENCE
  PLAN.MD:61   "User installs the app and does nothing. No Termux, no Linux,
                no API key hunting, no boot scripts, no configuration."
  PLAN.MD:150  "Resolution: Bring-Your-Own-Key (BYOK) for Tier 1. The user
                pastes their own Gemini key into a Keystore-backed screen."
  PLAN.MD:567  "Gemini BYOK = friction vs. 'user does nothing' -> accept"

IMPACT
  This is the #1 drop-off point of any consumer app: install -> "go get an
  API key" -> abandon. The entire product pivot ("user kuch na kare")
  stands or falls on this. Right now the plan states a promise it does
  not keep.

RECOMMENDED RESOLUTION  (both valid - owner picks)
  (a) Correct PLAN.MD:61 to state the real promise:
      "one-time setup: paste your own free Gemini key"
      Honest, zero server cost, Phase 1-7 complete with no backend.
  (b) Make CloudProxyBackend MANDATORY for the Play Store build.
      User does nothing; you run the proxy.
      Costs: server + abuse protection + rate limiting.

  Recommended: (a) for Phase 1-7. Decision (b) deferred to Phase 17.

A3  [BLOCKING for Tier 2]  Cleartext HTTP blocked for OpenCodeBackend
--------------------------------------------------------------------------------

CONFLICT
  OpenCodeBackend targets http://127.0.0.1:4096 which is cleartext HTTP.
  targetSdk 28+ blocks cleartext by default. Android grants NO automatic
  exemption for localhost.

EVIDENCE
  PLAN.MD:314   "| `OpenCodeBackend` | 2 | HTTP `127.0.0.1:4096` |"
  PLAN.MD:453   targetSdk 36  -> cleartext blocked by default

IMPACT
  Phase 12 fails at RUNTIME with:
      CLEARTEXT communication to 127.0.0.1 not permitted
  Discovered only after the client is written and debugged.

RECOMMENDED RESOLUTION
  Add res/xml/network_security_config.xml, scoped tightly to localhost only:
      <network-security-config>
        <domain-config cleartextTrafficPermitted="true">
          <domain includeSubdomains="false">127.0.0.1</domain>
          <domain includeSubdomains="false">localhost</domain>
        </domain-config>
      </network-security-config>
  Reference it from the manifest. Tier 1 does not need it (Gemini = HTTPS).

A4  [Tier 2]  Termux RUN_COMMAND cannot stream
--------------------------------------------------------------------------------

CONFLICT
  The plan promises stdout/stderr streaming. Termux:API's RUN_COMMAND intent
  returns output in a broadcast result - it is not a streaming API.

EVIDENCE
  PLAN.MD:277   "Input, stdout/stderr streaming, process state, ..."
  PLAN.MD:287   "output streaming, progress, APK discovery, ..."
  PLAN.MD:533   Phase 9 "... ANSI parser, streaming, Ctrl+C"

IMPACT
  A 5-minute assembleDebug would run with an empty screen, then dump all
  output at once. The terminal would look hung. Real UX impact on Tier 2.

RECOMMENDED RESOLUTION
  Redefine honestly as polling:
    "polling-based streaming: RUN_COMMAND launches in background, output is
     redirected to a temp file, app tails that file every 1-2 s."
  Write this explicitly into Phase 9 scope. A true PTY is not available
  through Termux:API - accept that as a known limitation.
