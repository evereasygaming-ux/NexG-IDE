================================================================================
  This is the only substantive difference between the two versions in this
  codebase, and it is worth recording because it looks like a failure if you are
  not expecting it.

  Room 2.6.1  ->  app/build/generated/ksp/debug/java/.../NexGDatabase_Impl.java
  Room 2.7.1  ->  app/build/generated/ksp/debug/kotlin/.../NexGDatabase_Impl.kt

  2.7.x generates Kotlin by default. So a search for NexGDatabase_Impl.java
  returns nothing under 2.7.1. That is NOT a build failure and NOT a missing
  file — the impl moved to .kt. Phase 2 documentation referred to
  NexGDatabase_Impl.java and is now stale on that detail.

  Generated impls present after the 2.7.1 run (regenerated 12:21:44, minutes
  before the final gate, so they are not stale 2.6.1 leftovers):
    NexGDatabase_Impl.kt
    ProjectDao_Impl.kt
    RecentFileDao_Impl.kt
  Exactly the three @Database / @Dao types this project declares. No unexpected
  extra generated types.

  Compiled artefacts present, confirming the Kotlin impl is really used:
    app/build/tmp/kotlin-classes/debug/com/nexg/ide/data/db/NexGDatabase_Impl.class
    app/build/intermediates/project_dex_archive/.../NexGDatabase_Impl.dex

  not a risk for this project — the whole data layer is already Kotlin, and the
  81 tests exercise the repositories through interfaces, not generated code.

5. THE ORIGINAL 2.7.1 FAILURE WAS NEVER ABOUT ROOM
================================================================================
  2.7.1 was originally rejected with:

    :app:kspDebugKotlin
      androidx.room.processor.DatabaseProcessor
        -> androidx.room.verifier.DatabaseVerifier.<clinit>
          -> No native library found for os.name=Linux, os.arch=aarch64

  That was a FALSE ATTRIBUTION. The real cause was the runtime, not the version:
  the build was running the Termux JDK (bionic) on a proot Ubuntu/glibc
  filesystem, so org.sqlite.JDBC could not dlopen its native library —

    UnsatisfiedLinkError: ...libsqlitejdbc.so: dlopen failed:
      library "libm.so.6" not found

  Isolated proof, outside Gradle: with the Ubuntu JDK on PATH this works. Also
  both cached compiler jars carry the same verifier and the same pinned
  sqlite-jdbc 3.41.2.2, and neither offers any option to skip verification:

    room-compiler-2.6.1.jar  ->  verifier/DatabaseVerifier PRESENT
    room-compiler-2.7.1.jar  ->  verifier/DatabaseVerifier PRESENT
    both                    ->  org.xerial:sqlite-jdbc:3.41.2.2

  So no Room version could ever have passed under the Termux JDK, and 2.6.1 only
  started working once the JDK was fixed. This test closes the loop: with the
  correct JDK, 2.7.1 — the version that was blamed and abandoned — passes both
  gates with the full 81 tests. The 2.6.1 pin was a workaround for the wrong
  diagnosis and is now obsolete.

7. RESIDUAL RISK — unchanged by this test
================================================================================
  * Both versions were exercised on the JVM and in a debug build only.
    No release build, no device run, no instrumented test, no migration test.
  * exportSchema = false in BOTH versions. room.schemaLocation must be enabled
    before the first schema change or the migration cannot be diffed afterwards.
    Nothing about this test makes the schema story safer; it is unchanged.
  * Choosing 2.7.1 means a newer Room whose future minor releases will keep
    moving (and 2.7.x already has a different artifact layout — see section 4).
    2.6.1 is the conservative pin. The trade is: 2.7.1 is the version this
    project was originally meant to be on, passes today, and is better supported
    going forward; 2.6.1 is only defensible as "pin what is proven older".
  * No behavioural difference was observed in any test. But "no test failed" is
    not "no behavioural difference" — the 81 tests do not exercise Room
    migrations, multi-instance invalidation, or Flow query semantics specifically.
